# 2026-11-22 Dry Mic stutter and audio recovery

## Capture corruption

Parley dictations recorded from **GoXLR Dry Mic** sounded chopped up. The same
corruption was present in a direct capture from the virtual input. The meter
recorded the physical 23-channel GoXLR Full and the virtual inputs concurrently
at 48 kHz. It compared zero-based physical channel 22 with Dry Mic, channel 18
with the left channel of Line-In, and channel 2 with the left channel of
Microphone.

The old [driver](../Driver.cpp) read capture data from a cursor initialized for
each client and ignored the requested CoreAudio sample time. If two 512-frame
requests started 416 frames apart but their cursors pointed at the same source
frame, the second reply overwrote the 96-frame overlap with a copy of the first
96 frames. A libASPL callback probe reproduced that exact case. One incident
recording contained the bit-exact duplicate in 754 of 755 Dry Mic blocks. The
original HAL request timestamps were unavailable for that recording. In a
separate live run, attaching a second client at a 76-frame offset shifted the
captured signal relative to the physical input by 76 frames. The shift reverted
when the client detached. Line-In also lost alignment with two clients.

Fix `e139bc4` indexes capture history by the requested sample time. Both ends of
each capture route use a shared, host-based 48 kHz timeline with 1,024 frames
(21.33 ms) of capture latency. The
[ring regression test](../tests/StereoHistory.cpp) covers overlapping mono reads
at the 416-frame offset, repeated reads, and a gap when the writer restarts.

| Route | Meter clients | Before, tolerance | After, tolerance | After, reconstructed Bridge output |
| --- | ---: | ---: | ---: | ---: |
| Dry Mic | 1 | 99.98% / 0 | 89.79% / 0 | 100% / 0 |
| Dry Mic | 2 | 85.18% / 502 | 86.64% / 8 | 100% / 0 |
| Line-In | 1 | 100% / 0 | 100% / 0 | 100% / 0 |
| Line-In | 2 | 0.25% / 541 | 100% / 0 | 100% / 0 |
| Microphone | 1 + Discord | 89.36% / 0 | 99.997% / 0 | 99.997% / 0 |
| Microphone | 2 + Discord | 90.02% / 0 | 99.958% / 1 | 99.958% / 1 |

Cells give the percentage of matching samples and the number of consecutive
mismatch runs of at least 16 frames after integer-lag alignment. The tolerance
comparison used `atol=1e-7` and `rtol=1e-5` and trimmed 1,000 leading and 10
trailing frames from the overlap. The reconstruction column compares
float bits after applying the bridge's existing linear interpolation with one
constant fractional phase. A phase of about 0.001096 samples reproduced all
Dry Mic samples in both after runs, including an additional run at a higher
signal level. The post-fix Dry Mic recordings contained no 416/96 repeats.
Microphone was nearly silent during the main runs. Its figures give limited
evidence about speech fidelity. The capture WAVs contain local audio and are kept
outside the repository.

## Driver installation and USB recovery

The first update printed `Bootstrap failed: 5: Input/output error`.
`launchctl bootout` had returned while the GUI-domain LaunchAgent was still being
removed. launchd rejected the early bootstrap with
`37: Operation already in progress` and completed removal about five seconds
later. The earlier update script restored the old HAL bundle and brought the
LaunchAgent back up.

[update-local.sh](../update-local.sh) waits for the job to leave the GUI domain
before starting it again as the logged-in user. It saves the old driver outside
the HAL directory and skips the driver swap on a retry with the same signed
build. The updated driver was verified by matching the installed binary to the
tested build and reading the 1,024-frame capture latency from CoreAudio.

After the CoreAudio restart, the GoXLR was present on USB but absent from the
CoreAudio device list even with the old driver restored. The daemon logged
`Audio Device Not Found` and the virtual devices delivered silence. If that
recurs, check `system_profiler SPAudioDataType` for the physical **GoXLR** with 23
inputs and 10 outputs. Unplug and reconnect its USB cable if the physical device
is missing. Then check the daemon log for
`GoXLR virtual audio bridge started` and verify both capture and playback.

## Silent system alerts after audio returned

Regular audio and Discord voices were audible, while macOS alerts, Parley's
dictation cue, and Discord event sounds were reported missing. Both the default
output and the alert output pointed to **GoXLR System**. The alert volume was
100%, and the System channel was routed to headphones, line out, and Broadcast
Mix at a nonzero level.

The short `Tink` sound reached the physical GoXLR from an idle virtual Game
output and again with a continuous stream on Game. It also reached the physical
device from System, Chat, and Music. Before and after `e139bc4`, the libASPL
callback probe delivered all 8,385 frames, including the last partial block read
after the writer stopped. That playback path continues to append to the history
and use a bridge-reader cursor. The shared capture timeline belongs to the
opposite direction.

Native AppKit and AudioServices alert calls failed to start audio I/O even
with the built-in speaker selected for sound effects. Direct playback activated
that speaker immediately afterwards. The test restored the original sound
effects output. An isolated playback test using Parley's Rodio version and
configured start cue reached the physical GoXLR. The actual Parley and Discord
event paths were not reproduced during these tests. The macOS alerts later
returned on their own with the same driver still installed. The exact cause of
the alert failure and recovery remains unknown.

If it recurs, play a short file through the affected virtual output and check
the corresponding physical loopback channel. Compare that with a native alert
from **System Settings → Sound → Sound Effects**. Check the output selected for
effects, alert volume, and the GoXLR route to the monitoring output. If ordinary
PCM reaches the hardware but the native preview is silent, try the built-in
speaker for effects, restore the preferred output after the test, and restart
macOS if the native preview is still silent.

## Pre-install checks

Run the ring and [short playback callback test](../tests/Playback.cpp) on every
driver change before installation. Keep one-client and two-client capture runs
and an idle-versus-running short-tone baseline for the installed build. Repeat
them on the candidate after installation and check the physical GoXLR and the
native alert path separately. See the [measurement guide](../tools/README.md).
